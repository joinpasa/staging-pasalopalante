## 2026-09-10 — va.deedumlao@gmail.com

- **Added a daily email digest of acts awaiting manual review**, sent to kindnessforward.26@gmail.com, so this no longer requires manually checking SQL to know something needs a look. Skips sending entirely on days with nothing pending, rather than an empty email every day. New `pending-review-digest` function — needs a one-time schedule set up in the Supabase dashboard (Integrations → Cron Jobs) since that's not something a migration should embed credentials to automate; see the reply for exact steps and the UTC time to use for 5pm Pacific.
  - **Now live**: scheduled directly via a `pg_cron` job run in the SQL editor (daily at 5pm Pacific), with the service role key stored in Supabase Vault rather than in the job's plain-text command — nothing left to set up.

- **"My Personal Commitment" now shows on the app dashboard too — pledge count, countdown to Global Kindness Season, progress once it starts, and the ability to edit the pledge — previously website-only.** Someone who set a pledge in onboarding had no way to see or change it again once they left that one-time screen, unless they happened to open the website. Same data, same edit behavior, just styled to match the app.
- **Fixed the Pass QR code linking to the dead `app.pasalopalante.com` subdomain.** It was hardcoded into what the QR encodes, the link shown under it, and the "Share my link" button — so anyone scanning someone else's pass with their phone's camera (not the in-app scanner, which never hit this since it reads the code directly) landed on the 522 error. Now built from the same same-origin app URL used everywhere else, so it correctly points at `pasalopalante.com/app/...`.
- **In-person Pass connections (scanning or being scanned) now show up on the app dashboard as a new "Connections" stat, with a people icon**, underneath the existing three stat boxes — only once you've actually made one, so it doesn't clutter the dashboard for everyone else. This was tracked in the database the whole time (a `pass_handoffs` table, separate from referral joins) but never surfaced anywhere in the app, so connecting with an existing member — like scanning a friend's code in person — looked like it did nothing. "People you passed to" is intentionally left as-is; it specifically counts people who joined the platform using your code, a genuinely different thing from an in-person connection between two people who already both have accounts.
- **The "I Did an Act of Kindness" label on the share form is now tappable, not just decorative text** — tapping it jumps straight back to re-pick how the act happened ("Did," "Received," or "Witnessed") instead of needing to notice the separate small "Back" link above it. Useful right after a Pass connection, where "I gave [kindness] to them" fits better than the default "I did."
- **The Connections stat card on the app dashboard is now tappable and opens a list of everyone you've connected with in person via Pass** — name and when, most recent first. New `/connections` page in the app.
- **Fixed "Acts all time" barely moving despite real new acts being logged.** Root cause: submit-act holds an act as unpublished ("pending") whenever AI moderation doesn't come back with a clean "approved" — including whenever the AI moderation service itself is down or rate-limited, which says nothing about the content but was quietly piling acts up outside every public count (Wall, Map, this total) with no way to see or clear the backlog except raw SQL. One-time fix republishes every act that was stuck specifically because the AI service was unavailable; acts the AI actually reviewed and was genuinely uncertain about are left pending for real review, unchanged. Confirmed there's currently no notification when this happens at all (`should_alert_admin` was computed and returned in the API response but never actually used to alert anyone) — next up is a real one, plus a proper review screen instead of SQL.

## 2026-09-09 — va.deedumlao@gmail.com

- **Fixed the Portuguese translation's word for "kindness."** The DeepL machine translation had inconsistently used "Bondade" (a literal but not how Brazilian Portuguese speakers actually say it) in some places and the natural "Gentileza" in others — including the hero headline, which is what got flagged. Replaced every "Bondade"/"bondade" with "Gentileza"/"gentileza" throughout (69 instances), so the wording is consistent everywhere in Portuguese, not just the headline.
- **Fixed the QR scanner (Pass → Scan) showing a black camera feed even after allowing camera access.** The permission and the camera stream were both fine — the video element the stream was attached to just never actually started playing. The `autoplay` attribute alone doesn't reliably start playback for a camera stream assigned to a video element programmatically after the page has already loaded (a well-known gap, most notably on iOS Safari); it needs an explicit `.play()` call, which was missing. No error, no permission prompt issue — just a silently-never-started video, indistinguishable from a broken camera.
- **Fixed the code/link still showing "expired" immediately after receiving it, and added a "Resend code" option.** Yesterday's fix (routing the email link through the app's own domain) stopped a *simple* email-scanner prefetch from burning the token, but some email security scanners go further and fully render the destination page — including running its JavaScript — specifically to catch phishing redirects, which silently triggered our own auto-verify-on-load code the same way a real visit would. Verifying now requires an explicit tap ("Tap to finish signing in") instead of firing automatically on page load — something no scanner simulates, so a scanner's visit does nothing at all, while a real visit costs one extra tap. Also added a "Resend code" button right on the "check your email" screen, so a burned or missed code doesn't require starting over.
- **Fixed "Forgot password" / "Reset password" leading to a 404, on both the app and the website.** Root cause: the reset-password email correctly linked to `/reset-password`, but that page had never actually been built anywhere in the codebase — the link was always going to 404, on any account, from either app. Built the missing page (on the website, since the app and website now share one origin, so a single page covers a reset started from either place) — it picks up the recovery session Supabase's own link already establishes, lets you set a new password, and shows a clear "this link expired, request a new one" message if the link is stale or already used, instead of a bare 404.
- **App badges now match the website's** — same catalogue, same categories (streak badges vs. the act-type badges), same real icons, same localized names, and the same streak stats (current streak, longest streak, total acts) that were only ever shown on the website's account page. Previously the app showed every badge in one flat, un-categorized grid with a generic letter avatar instead of each badge's actual icon, and had no streak info at all — it looked like a different, less finished feature even though it was reading the same data. The Home dashboard's "Badges earned" preview strip got the same real-icon fix.
- **The Wall now shows the worldwide movement totals (acts pledged, logged today, acts all time) regardless of whether you're signed in.** Those numbers previously only appeared on the Home dashboard, and only to a signed-out visitor — once you're signed in, Home switches to your own personal stats and the worldwide numbers disappear entirely, with nowhere else in the app to see them. The Wall is the natural place for the movement-wide numbers to always be visible, for anyone.
- **Fixed "Skip for now" on the welcome walkthrough looking broken.** It was actually working correctly — it disables itself while it saves your pledge and syncs your info in the background — but the label never changed while that happened, so tapping it looked like nothing happened. It now shows "…" while it's working, matching how the other buttons in the same flow already behave. (Confirmed via an isolated test that the skip action itself always fires correctly once someone's name/country are on file, which they are by the time anyone reaches this screen from the Join form.)
- **Fixed two bugs in yesterday's new code-entry sign-in: the code field only accepted 6 digits (Supabase's actual current default is 8, and it's configurable up to 10), and codes were showing "expired" the instant they were used.** The second one was the real find: Supabase's confirm link verifies — and permanently consumes — the token on a plain visit, and email security scanners (Gmail, Outlook, corporate mail gateways) routinely prefetch links in emails to check they're safe, silently burning the token before the recipient ever opens the email themselves. Since the code and the link share the same underlying token, that also broke the code the moment the scanner touched the link. Signup and sign-in emails now point at our own app instead of Supabase's raw verify link; the app itself completes verification via real page JavaScript, which a scanner's plain fetch can't trigger. The code input no longer assumes a fixed digit count either.
- **Fixed the sign-in-by-email-link loop on the installed app, especially on iPhone.** Root cause, confirmed against Apple's own bug tracker: iOS deliberately keeps Safari's storage separate from an already-installed home-screen app's storage, even for the same site — so tapping the link in the verification/sign-in email opens Safari, completes there, and the already-installed app never sees it, leaving someone stuck signed out no matter how many times they tap the link. The fix: the confirmation/sign-in email now also includes the 6-digit code Supabase was already generating (just never showing), and both the Join screen and the in-app "verify your email" banner now let someone type that code directly into the already-open app instead of leaving it — completing sign-in with no browser hop at all, so the loop can't happen. The link stays as the primary option for everyone else.
- **Redesigned the iOS "how to install" instructions to be readable at a glance, and added a direct link to the app.** iOS (Safari and Chrome both — Apple requires every iOS browser to use the same engine, and Apple has never added a way for any website to trigger a one-tap install there; confirmed still true as of today against current sources) can only ever offer a manual "tap Share, then Add to Home Screen" step — no site can make that automatic. The instructions now use big numbered steps with icons instead of a paragraph to read, and include a direct "Get the app" link so someone can jump straight to the simpler, uncluttered app screen and do Add to Home Screen from there instead of hunting for that link elsewhere on the homepage.

- **Fixed the homepage's install button on iOS (Safari and Chrome — both are Apple-mandated WebKit under the hood, so both behave identically here).** No browser on iOS ever supports the one-tap native install dialog — that's an Apple platform restriction, not something any site can change; the correct experience there has always been the manual "tap Share → Add to Home Screen" steps. But the homepage's install card didn't know it was on iOS, so tapping "Get the app" was sending iOS users into `/app/` first and only showing the real instructions after that second stop — an unnecessary extra hop, and a different (worse) experience than what Android/desktop Chrome now get directly on the homepage. It now shows the real Add to Home Screen steps right on the homepage, in place, for both Safari and Chrome on iOS. Verified locally against a Cloudflare-equivalent build (service worker, manifest, and header behavior all match production) — Android Chrome and desktop are unaffected by this change.

## 2026-09-08 — va.deedumlao@gmail.com

- **Added three new "Get Involved" landing pages with embedded sign-up forms**: `/get-involved/schools` (Schools & Educators), `/get-involved/nonprofits` (Nonprofits & Faith Communities), and `/get-involved/ambassadors` (Ambassadors), each embedding the GoHighLevel form for that audience. The matching cards on `/get-involved` now link to these instead of the generic Contact/Commit pages.
- **Every "Download/Get/Open the app" button on the website now triggers the same real one-tap native install** used by the floating install card — not just that card. The How It Works section's "Open the app" button and the Account Settings page's "Download the app" button were still plain links that opened `app.pasalopalante.com` in a new tab (which can never trigger an install — a new background tab has no install prompt to use, and it also predated the domain merge). Both now call the same install trigger: a real native install dialog when the browser has one ready, same-tab fallback to the app otherwise. This applies equally on mobile browsers, since it's the same standard web install mechanism Chrome/Edge use everywhere, not something specific to one entry point.
- **Installing from the homepage now lands on the app dashboard immediately, without closing and reopening.** When someone installs from the marketing homepage (the new one-tap flow), the browser converts that same tab into the app's window without navigating it — so it kept showing the homepage right after "Install," which is exactly what confused a team member into trying to sign in there and getting looped. The redirect-to-app logic only ever checked once, when the page first loaded as a normal tab (before the install happened) — it had no way to know the tab had since flipped into the installed app. It now listens for that flip live (the display-mode change plus the browser's own "appinstalled" event) and redirects to the dashboard the instant it happens, no reload needed. Also fixed the redirect target itself to respect the new combined domain (same-origin `/app/`) instead of always pointing at the old `app.pasalopalante.com` subdomain.
- **"Install app" now shows up reliably from the very first visit.** The mechanism was already right — tapping the button opens the browser's own native install confirmation, same as the old Lovable build did — but the service worker it depends on only registered after someone turned on push notifications, so on a fresh visit the button could just fail to appear. It now registers eagerly on page load instead, on both the website and the app. Also fixed the push notification icon pointing at a path that never existed.
- **Fixed the website claiming the app was already installed when it wasn't.** Root cause: the website has no PWA manifest of its own, so the browser's real "is this already installed" signal could never fire there — every visit, installed or not, fell into a fallback that assumed "already installed." The website now just always offers a "Get the app" link to the actual app, where the real install flow lives (that part already worked correctly and needed no change).
- **The app now lives at `pasalopalante.com/app/*`**, on the same domain as the marketing site instead of its own subdomain. `app.pasalopalante.com` still exists for anyone with an old bookmark or a previously-shared Pass QR code, and can be pointed at a redirect once this is confirmed stable — not done yet.
  - Getting the Cloudflare side actually live took three follow-up rounds after the initial cutover: Cloudflare's deploy validator rejected the first SPA-fallback rule as a false-positive "infinite loop" (fixed by renaming the fallback target); that led to an actual runtime redirect loop from Cloudflare's automatic `.html`-extension stripping (fixed by dropping the extension entirely); which in turn revealed the fallback's wildcard pattern was also shadowing the app's real JS/CSS files, breaking the whole page (fixed by listing the app's specific routes instead of a wildcard).
- **Tried, and had to walk back, auto-triggering the native install dialog right after "Get the app."** Chrome confirmed via its own error message: `.prompt()` requires a live user gesture at the moment it's called, and that doesn't survive a page navigation — no code, however triggered, can call it successfully after arriving from a link on another page. This is a hard browser rule, not a bug, so that auto-trigger code got removed again.
- **The homepage itself is now installable — the real fix, matching the old Lovable flow exactly: tap "Get the app," native dialog opens directly, no click-through first.** Previously only pages under `/app/*` carried the signal that tells the browser "this is installable" (a manifest + service worker); the homepage and every other marketing page had neither, which is why a navigation to the app was always required first. Every website page now links to the same manifest (widened to cover the whole site, not just `/app/*`) and can register the app's service worker at that same wider scope. The button on the homepage now behaves exactly like the one already on the app: a real tap opens the real native dialog, address-bar install icon and all — the extra "Get the app → land on the app → tap again" hop is gone entirely wherever the browser recognizes the page as installable; it only falls back to sending someone to the app when a direct install genuinely isn't available yet (iOS, or before beforeinstallprompt has fired). Confirmed live: the full tap → native dialog → Install → saved-to-device flow actually works now.
  - One follow-up found installing from the homepage: the newly-installed icon opened to the homepage instead of `/app/`, even though the manifest's `start_url` was correctly `/app/`. Chrome's own DevTools flagged the likely cause — no explicit manifest `id` means Chrome infers the app's identity from `start_url`, and across many iterations of this manifest being fetched mid-build (before `start_url` was even correct), it's plausible Chrome locked onto a stale inferred identity. Pinned `id` explicitly instead of leaving it inferred. Not yet confirmed fixed live.

## 2026-09-02 — va.deedumlao@gmail.com

The busiest day so far — most of today was root-causing and fixing why acts of kindness sometimes failed to submit, plus a big batch of app/website parity work.

- **Wall of Kindness was empty / public data wasn't loading.** Root cause: Supabase had disabled the old JWT-format API key project-wide. Fixed by switching the app and website to the new `sb_publishable_...` key everywhere, and moved every public/anonymous read (wall, map, badges, reactions, streaks) onto a session-free Supabase client so a signed-out visitor's page doesn't depend on having a session at all.
- **"Something went wrong" / 429 / 500 on submitting an act of kindness — fully resolved**, in three parts:
  1. The AI moderation call (Gemini) has rate limits with no fallback — added one: if AI moderation is temporarily unavailable, the act is now held for manual review instead of the submission failing outright.
  2. Found and fixed a stale local deploy issue (uncommitted local files were silently overriding what got pushed to GitHub every time functions were redeployed).
  3. Found a real bug underneath both: held-for-review acts were being saved with a status value the database didn't actually allow, causing a hard failure. Fixed the status value.
- **App login brought up to parity with the website's**: forgot-password flow, magic-link cooldown, clearer error messaging for accounts that don't have a password set yet.
- **Pass QR (in-person "connect" hand-off) — several real bugs fixed:**
  - Codes always said "not valid" — a case-sensitivity mismatch between how codes were generated (lowercase) and how they were displayed/scanned (uppercased somewhere in the middle).
  - Scanning someone's pass while already having the app installed never actually connected/attributed the referral, and an in-app scan showed "success" but never navigated anywhere.
  - The QR code's "Save" button was a stub — wired it up to actually download a real image.
- **Organization/group pledges**: fixed missing GHL tags (`get-involved-group`, and tags for every org type including `faith`/`other`), and Pledge vs. Commitment now sync to two separate GHL fields instead of one overwriting the other.
- Restored the app's Home dashboard as the landing page for signed-out visitors; removed a redundant "Join to unlock the full app" banner (kept the dashboard card + bottom popup); the Install Prompt no longer overlaps the Share Act dialog; added a downloadable QR code to the website's "Your Invitations" section; added Google Analytics to both apps; added Cayman Islands to the country list.
